# PHP API: этапы 1–3

Реализованы основа API, реальный вход через `legacy_poly.user_list`, серверные сессии, роли `admin` / `rop` и операции справочников. Таблицы школ, преподавателей, направлений, программ, дисциплин, внешних участников и карточек председателей читаются и сохраняются в PostgreSQL. Схема БД не меняется. Комиссии, ООП, архив и печать подключаются следующими этапами.

## Запуск локально

Нужны PHP 8.2+ с расширениями `pgsql`, `mbstring` и действующая PostgreSQL. Скопировать `config.example.php` в `config.local.php`, заполнить пароль подключения и точные логины в `roles`. Локальный файл, сессии и ограничитель входа исключены из Git.

Согласованное назначение: логин `admin` — роль `admin`, логин `rop` — роль `rop`. Пароли пользователей берутся из БД, в конфигурацию ролей не записываются. Пользователю без назначения роли вход закрыт.

Из корня репозитория в двух терминалах:

```powershell
php -S 127.0.0.1:8081 -t backend/public backend/router.php
npm run dev
```

Vite перенаправляет `/api` в PHP. Встроенный PHP-сервер предназначен только для локальной разработки. При размещении приложения настроить веб-сервер: `/api/v1/*` направлять в `backend/public/index.php`, выдавать фронтенд из `dist`, закрыть доступ к остальному каталогу backend. Использовать HTTPS и `secure_cookie=true`. Сессия действует 30 минут бездействия, не более 8 часов с момента входа.

## Контракт

| Запрос | Результат |
|---|---|
| GET `/api/v1/health` | Доступность процесса и версия, без реквизитов БД |
| GET `/api/v1/auth/session` | `data.user` (или null), `data.csrfToken` |
| POST `/api/v1/auth/login` | JSON username/password, сессия и обновлённый CSRF |
| POST `/api/v1/auth/logout` | Удаление серверной сессии и cookie |
| GET `/api/v1/health/database` | Проверка БД, только администратор |
| GET `/api/v1/catalog` | schools, teachers, directions, programs, disciplines, levels |
| POST `/api/v1/catalog/{kind}/save` | Поля справочника, id (null при создании), version при изменении; ответ data.id |
| POST `/api/v1/catalog/{kind}/delete` | id и version; ответ data.deleted |
| GET `/api/v1/people` | people и entries: external, chairmen, complex |
| POST `/api/v1/people/{category}/save` | id, version; person для external или personId, sphere, schoolIds, values для карточки |
| POST `/api/v1/people/{category}/delete` | id и version; ответ data.deleted |

Справочники доступны обеим согласованным ролям. Каждый полученный ряд содержит `version`; при несовпадении версии запись отклоняется с 409 STALE_RECORD. После сохранения клиент перечитывает данные. Нет автоматического возврата к локальным данным при ошибке API. Ответ 409 IN_USE означает наличие зависимых данных, 422 — ошибку полей или выбранной связи.

## Связи и ограничения этапа 3

- `teacher.id_teacher` — табельный номер, вводится при создании, сохраняется как строка с ведущими нулями и не переименовывается.
- Направление связано с несколькими программами по `id_direction`; программа идентифицируется `id_mep`. При изменении её кода обновляются старые текстовые связи `sec_program.id_program` в той же транзакции.
- Директор и его должность, включая и.о., остаются полями высшей школы. Новый справочник директоров не создаётся.
- Председатели ссылаются на `sec_member`. Для преподавателя без записи участника она создаётся по табельному номеру; людей по совпадению ФИО не объединяем. Уже существующие записи `teacher` и `sec_member` не синхронизируются автоматически: это разные записи старой схемы.
- У одного участника одна карточка среди обычных и комплексных председателей, как в старом обработчике. Школа обычного председателя хранится в `sec_helper`, школы комплексного — в `sec_complex_sc`. Список школ заменяется целиком в транзакции. `sec_as` — служебная таблица старой печати, её не используем как связь школ.
- Поля сфер «Образование» и «Бизнес» различаются. Не переданные поля сохраняются, связи программ комплексной карточки не перезаписываются формой.
- Проверяются внешние ключи, включая каскадные удаления, и известные связи старой схемы без FK. Используемые записи не удаляются. При удалении свободной карточки удаляются её собственные связи, сам участник остаётся.
- В рабочей БД обнаружены две карточки без участника. Они теперь видны с предупреждением; автоматической подстановки человека или удаления нет. Для восстановления принадлежности нужно уточнение пользователя.
- В старом добавлении председателя есть создание папки архива. Корневой каталог и необходимость этого действия запрошены у пользователя; до ответа эта связь с файловым архивом не подключена. Сами файлы и шаблоны печати не изменялись.
- Источники справочников на страницах `/data/catalog/*` и `/data/people/*` серверные. Старые локальные справочники остаются только в ещё не подключённых модулях комиссий и ООП; их замена входит в этапы этих модулей. Учебный период пока не переключает БД.

На POST требуется заголовок `X-CSRF-Token` из текущей сессии. Cookie HttpOnly, SameSite=Lax. После входа идентификатор сессии и CSRF обновляются. Допустимые ошибки: 400/415 — формат запроса, 401 — вход, 403 — доступ/CSRF, 422 — поля, 429 — попытки входа, 503 — недоступность БД. Ответ: `error.code`, `error.message`, `error.fields`, `error.requestId`. В журнале сервера только код ошибки и идентификатор запроса, без паролей и SQL.

Сервер закрывает РОП маршруты `/api/v1/oop/directions` и `/api/v1/oop/general`, включая вложенные URL и любые методы. Администратор получает 501: обработчики данных этих этапов ещё не реализованы. Фронтенд закрывает соответствующие страницы, скрывает карточки, навигацию и поиск. Остальные права не ограничиваются дополнительно. Будущие обработчики этих модулей должны располагаться после проверки роли; альтернативные URL не должны обходить её.

## Совместимость паролей

Поддерживаются `password_verify` для существующих PHP-хешей и сравнение текущего старого формата через `hash_equals`. Пароли и их формат в БД не меняются автоматически, чтобы не нарушить вход в старое приложение. Перевод хранения на хеши остаётся отдельным согласуемым шагом. Запрос поиска пользователя параметризован; дублирующиеся логины отклоняются.

## Проверки

```powershell
# Установить локально TEST_ADMIN_PASSWORD и TEST_ROP_PASSWORD, не добавляя их в Git.
node backend/tests/auth.mjs
node backend/tests/catalog-browser.mjs
php backend/tests/catalog.php
npm test
npm run build
```

Тест проверяет настоящий вход обоими пользователями без записи в БД, обновление страницы, выход, отклонение SQL-инъекции, CSRF, cookie, запреты интерфейса и API. Локальные проверки прежних экранов, использующие кнопку заполнения фиксированных реквизитов, требуют перехода на реальный вход перед следующим запуском.

`catalog-browser.mjs` проверяет пять реальных справочников, три таблицы людей и открытие карточек обеими ролями; ошибки сохранения и недоступность API проверяются подменой ответов только в тестовом браузере. Рабочие данные не редактируются.

`catalog.php` создаёт только временные таблицы текущего соединения по существующей схеме, с отдельными последовательностями и копиями внешних ключей. Все записи синтетические; рабочие строки, последовательности и схема public не изменяются. Проверены CRUD, обязательные поля, неверные связи, дубликаты, конфликт версий, атомарность, обе сферы, школы, табельный номер, переименование кода программы и запрет удаления связанных данных.
