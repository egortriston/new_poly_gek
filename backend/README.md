# PHP API: этапы 1–3 и архив

Реализованы основа API, реальный вход через `legacy_poly.user_list`, серверные сессии, роли `admin` / `rop`, операции справочников и серверный архив. Таблицы школ, преподавателей, направлений, программ, дисциплин, внешних участников и карточек председателей читаются и сохраняются в PostgreSQL. Схема БД не меняется. Комиссии, ООП и печать подключаются следующими этапами.

## Запуск локально

Нужны PHP 8.2+ с расширениями `pgsql`, `mbstring` и действующая PostgreSQL. Скопировать `config.example.php` в `config.local.php`, заполнить пароль подключения и точные логины в `roles`. Локальный файл, сессии и ограничитель входа исключены из Git.

Согласованное назначение: логин `admin` — роль `admin`, логин `rop` — роль `rop`. Пароли пользователей берутся из БД, в конфигурацию ролей не записываются. Пользователю без назначения роли вход закрыт.

Из корня репозитория в двух терминалах:

```powershell
php -S 127.0.0.1:8081 -t backend/public backend/router.php
npm run dev
```

Vite перенаправляет `/api` в PHP. Встроенный PHP-сервер предназначен только для локальной разработки. При размещении приложения настроить веб-сервер: `/api/v1/*` направлять в `backend/public/index.php`, выдавать фронтенд из `dist`, закрыть доступ к остальному каталогу backend. Использовать HTTPS и `secure_cookie=true`. Сессия действует 30 минут бездействия, не более 8 часов с момента входа.

## Контракт

| Запрос | Результат |
|---|---|
| GET `/api/v1/health` | Доступность процесса и версия, без реквизитов БД |
| GET `/api/v1/auth/session` | `data.user` (или null), `data.csrfToken` |
| POST `/api/v1/auth/login` | JSON username/password, сессия и обновлённый CSRF |
| POST `/api/v1/auth/logout` | Удаление серверной сессии и cookie |
| GET `/api/v1/health/database` | Проверка БД, только администратор |
| GET `/api/v1/catalog` | schools, teachers, directions, programs, disciplines, levels |
| POST `/api/v1/catalog/{kind}/save` | Поля справочника, id (null при создании), version при изменении; ответ data.id |
| POST `/api/v1/catalog/{kind}/delete` | id и version; ответ data.deleted |
| GET `/api/v1/people` | people и entries: external, chairmen, complex |
| POST `/api/v1/people/{category}/save` | id, version; person для external или personId, sphere, schoolIds, values для карточки |
| POST `/api/v1/people/{category}/delete` | id и version; ответ data.deleted |
| POST `/api/v1/people/{chairmen|complex}/archive` | id, version, academicYear; создаёт или открывает папку архива председателя |
| GET `/api/v1/archive/list` | Содержимое папки архива, до 50 объектов, total и nextCursor |
| GET `/api/v1/archive/context` | Текущая папка, хлебные крошки и лимит файла |
| GET `/api/v1/archive/download` | Скачивание файла из архива |
| POST `/api/v1/archive/upload` | Загрузка файла в папку архива |
| POST `/api/v1/archive/{mkdir|rename|delete}` | Создание, переименование и удаление папок/файлов |

Справочники доступны обеим согласованным ролям. Каждый полученный ряд содержит `version`; при несовпадении версии запись отклоняется с 409 STALE_RECORD. После сохранения клиент перечитывает данные. Нет автоматического возврата к локальным данным при ошибке API. Ответ 409 IN_USE означает наличие зависимых данных, 422 — ошибку полей или выбранной связи.

## Связи и ограничения этапа 3

### Постепенная загрузка таблиц

Рабочие страницы используют GET `/api/v1/catalog/{kind}/list` и `/api/v1/people/{category}/list`. Ответ: `items` (до 50 записей), `nextCursor` (null в конце) и `total` — полное число результатов поиска и фильтрации. Интерфейс показывает только «Всего записей: …». Следующая порция автоматически запрашивается при прокрутке; DOM содержит только видимые строки и небольшой запас.

Параметры: `q`, `cursor`, `id` для прямого открытия; для программ — `id_direction`, преподавателей/дисциплин — `id_school`, направлений — `id_level`, председателей — `sphere` и `person`. Поиск выполняется в БД по всем подходящим записям и связанным названиям. Символы % и _ ищутся буквально. Курсор привязан к поиску и фильтрам, порядок задаётся неизменяемым идентификатором. При изменении запроса список начинается заново; устаревшие запросы отменяются, их ответы не применяются.

GET `/api/v1/options/{schools|directions|levels|people|chairmancandidates}` возвращает варианты тем же порционным контрактом. Параметр `id` отдельно разрешает выбранное значение, даже когда его нет в загруженных вариантах. `chairmancandidates` исключает людей, у которых уже есть карточка обычного или комплексного председателя. Выпадающие списки людей и справочников виртуализированы. Небольшой список школ для чекбоксов карточки берётся из `/api/v1/catalog/context`.

При сетевой ошибке загруженные строки сохраняются. Повторяется именно неудачный запрос — первая загрузка, обновление или продолжение. Старые полные GET `catalog` / `people` сохранены для совместимости и проверок, но эти страницы их больше не вызывают. Изменения других пользователей доступны после обновления списка; многозапросная прокрутка не удерживает долгую транзакцию БД.

Проверки: `php backend/tests/lists.php` (изолированные временные таблицы) и `node backend/tests/progressive-browser.mjs` (локальные реквизиты TEST_ADMIN_PASSWORD). Проверяются проход до конца, общее количество, поиск за первой порцией, фильтры, конфликт курсоров, отсутствие повторов, ограниченное число DOM-строк, ошибки/повтор, запоздалые ответы, прямые карточки и варианты селектора.

- `teacher.id_teacher` — табельный номер, вводится при создании, сохраняется как строка с ведущими нулями и не переименовывается.
- Направление связано с несколькими программами по `id_direction`; программа идентифицируется `id_mep`. При изменении её кода обновляются старые текстовые связи `sec_program.id_program` в той же транзакции.
- Директор и его должность, включая и.о., остаются полями высшей школы. Новый справочник директоров не создаётся.
- Председатели ссылаются на `sec_member`. Для преподавателя без записи участника она создаётся по табельному номеру; людей по совпадению ФИО не объединяем. Уже существующие записи `teacher` и `sec_member` не синхронизируются автоматически: это разные записи старой схемы.
- У одного участника одна карточка среди обычных и комплексных председателей, как в старом обработчике. Школа обычного председателя хранится в `sec_helper`, школы комплексного — в `sec_complex_sc`. Список школ заменяется целиком в транзакции. `sec_as` — служебная таблица старой печати, её не используем как связь школ.
- Поля сфер «Образование» и «Бизнес» различаются. Не переданные поля сохраняются, связи программ комплексной карточки не перезаписываются формой.
- Проверяются внешние ключи, включая каскадные удаления, и известные связи старой схемы без FK. Используемые записи не удаляются. При удалении свободной карточки удаляются её собственные связи, сам участник остаётся.
- В рабочей БД обнаружены две карточки без участника. Они теперь видны с предупреждением; автоматической подстановки человека или удаления нет. Для восстановления принадлежности нужно уточнение пользователя.
- Архив хранится в `storage/archive`, каталог исключён из Git и создаётся сервером при первом обращении. Файлы не раздаются напрямую веб-сервером: все операции идут через API с проверкой сессии и CSRF для изменений. Служебная папка `.polytech-storage` скрыта из списков. Символические ссылки и выход за границы архива запрещены.
- Для карточек председателей кнопка «Папка архива» создаёт или открывает папку `Председатели ГЭК {год окончания периода}/{id участника} — {ФИО}`. Для периода `2026/2027` используется год `2027`. Новая карточка председателя создаёт такую папку автоматически.
- Печатные шаблоны не изменялись. Кнопка перехода к печати ведёт в текущий раздел печатных форм; точные серверные шаблоны подключаются отдельным этапом, чтобы сохранить унифицированный формат.
- Источники справочников на страницах `/data/catalog/*` и `/data/people/*` серверные. Старые локальные справочники остаются только в ещё не подключённых модулях комиссий и ООП; их замена входит в этапы этих модулей. Учебный период пока не переключает БД.

На POST требуется заголовок `X-CSRF-Token` из текущей сессии. Cookie HttpOnly, SameSite=Lax. После входа идентификатор сессии и CSRF обновляются. Допустимые ошибки: 400/415 — формат запроса, 401 — вход, 403 — доступ/CSRF, 422 — поля, 429 — попытки входа, 503 — недоступность БД. Ответ: `error.code`, `error.message`, `error.fields`, `error.requestId`. В журнале сервера только код ошибки и идентификатор запроса, без паролей и SQL.

Сервер закрывает РОП маршруты `/api/v1/oop/directions` и `/api/v1/oop/general`, включая вложенные URL и любые методы. Администратор получает 501: обработчики данных этих этапов ещё не реализованы. Фронтенд закрывает соответствующие страницы, скрывает карточки, навигацию и поиск. Остальные права не ограничиваются дополнительно. Будущие обработчики этих модулей должны располагаться после проверки роли; альтернативные URL не должны обходить её.

## Совместимость паролей

Поддерживаются `password_verify` для существующих PHP-хешей и сравнение текущего старого формата через `hash_equals`. Пароли и их формат в БД не меняются автоматически, чтобы не нарушить вход в старое приложение. Перевод хранения на хеши остаётся отдельным согласуемым шагом. Запрос поиска пользователя параметризован; дублирующиеся логины отклоняются.

## Проверки

```powershell
# Установить локально TEST_ADMIN_PASSWORD и TEST_ROP_PASSWORD, не добавляя их в Git.
node backend/tests/auth.mjs
node backend/tests/catalog-browser.mjs
php backend/tests/catalog.php
npm test
npm run build
```

Тест проверяет настоящий вход обоими пользователями без записи в БД, обновление страницы, выход, отклонение SQL-инъекции, CSRF, cookie, запреты интерфейса и API. Локальные проверки прежних экранов, использующие кнопку заполнения фиксированных реквизитов, требуют перехода на реальный вход перед следующим запуском.

`catalog-browser.mjs` проверяет пять реальных справочников, три таблицы людей и открытие карточек обеими ролями; ошибки сохранения и недоступность API проверяются подменой ответов только в тестовом браузере. Рабочие данные не редактируются.

`catalog.php` создаёт только временные таблицы текущего соединения по существующей схеме, с отдельными последовательностями и копиями внешних ключей. Все записи синтетические; рабочие строки, последовательности и схема public не изменяются. Проверены CRUD, обязательные поля, неверные связи, дубликаты, конфликт версий, атомарность, обе сферы, школы, табельный номер, переименование кода программы и запрет удаления связанных данных.

### Идентификатор и печатный номер ГЭК

`sec.id_com_sec` — ГЭК ID: номер высшей школы и двухзначный порядковый номер внутри неё. При сохранении префикс приводится к выбранной школе; 00 и дубликаты отклоняются. Существующие записи массово не перенумеровываются.

Печатный номер: `37` + последние две цифры конца учебного периода + (`sec_info.number` + начало нумерации − 1), минимум две цифры. Выбор школы или отдельных комиссий не меняет глобальную нумерацию. Начало задаётся в «Формирование и печать» и применяется автоматически при открытии печатного документа; хранится по учебному периоду в игнорируемом `backend/var/gek-numbering.json` (по умолчанию 1). Схема БД не меняется. В `sec` нет периода: используется существующий общий список, выбранный период определяет печатный год.

Состав председателей формируется mPDF по вёрстке `chairmen-list.php`; направления и порядок берутся из прежних запросов. Учебный год подставляется также в дату подписания.

### Комиссии СПО

Раздел `/attestation/spo` подключён к существующим `spo` (только `ac=false`), `spo_teacher`, `spo_direction`, `spo_mep` и `cover_page` (`spo=true`). СПО и АК изолированы на сервере. Сохраняются версия записи и атомарные связи, проверяются повторные номера, участники и соответствие программ направлениям. При создании председателем по умолчанию назначается `25011`. Менять председателя может только admin: проверка действует в интерфейсе и API СПО. АК также подключён к серверу; изменение председателя проверяется в API по роли admin. Учебный период не создаёт отдельную копию списка: в существующей таблице нет поля периода.

Титульный лист школы — для служебной записки, общий — для распоряжения. Редактируются номер, дата и учебный период; остальной текст и фирменный бланк перенесены из `commissions/pdf/spo_pdf.php` старой системы. PDF генерирует mPDF. Под подписью замдиректора подставляется конец выбранного периода по согласованию с пользователем. Печать из таблицы учитывает выбранные комиссии либо весь результат поиска.

Проверки: `php backend/tests/spo.php` (только временные таблицы), `node backend/tests/spo-browser.mjs` с `TEST_ADMIN_PASSWORD` (чтение рабочих данных, проверка интерфейса и трёх вариантов PDF без изменения деловых записей).

### Аттестационные комиссии (АК)

`/attestation/ac` использует тот же серверный модуль, что СПО, с отдельными маршрутами `/api/v1/ac/*` и обязательным признаком `spo.ac=true`. Титульные листы выбираются по `cover_page.ac=true`; данные СПО не затрагиваются.

Специальные комиссии с внутренними ID 60 и 61 сохраняют исходные описания и запрет удаления, в том числе на сервере. Номер редактируется как в старой системе. Председателя меняет только admin; РОП может сохранять остальной состав с прежним председателем. Полнота специальных комиссий учитывает их общее описание направлений.

Печать перенесена из `commissions/pdf/ac_pdf.php`: собственный текст распоряжения и служебной записки, специальные пояснения, бланк и подписи. Генерация — mPDF, год подписи — конец выбранного периода. Проверки: `backend/tests/ac.php`, `backend/tests/ac-browser.mjs`.

### ППА

`/attestation/ppa` подключён к `certification` и четырём таблицам связей: преподаватели, направления, программы, дисциплины. Основные составы (`add_edit=false`) и изменения (`true`) разделены. Номера уникальны в пределах школы и списка, как раньше. Сохранение атомарное, с проверкой версий и ссылок; председатель ППА доступен для изменения обеим ролям.

В печати нет выбора школы: основное распоряжение и дополнение/изменение формируются по всем школам. Из таблицы можно печатать выбранные комиссии. Основной титульный лист выбирается по `ppa=true`, дополнение — по прежним признакам `spo=false, ac!=true, add_edit=true` (в старой БД у дополнений `ppa=false`). Реквизиты не смешиваются. Год текста берётся из выбранного учебного периода; даты и номера — из титульного листа.

mPDF-шаблоны перенесены из `certification_pdf.php` и `certification_add_pdf.php` без замены унифицированного содержания. Проверки: `backend/tests/ppa.php`, `backend/tests/ppa-browser.mjs`.


### ППА: режимы печати и проверка статуса ООП

ППА поддерживает распоряжение и дополнение по всем школам, а также служебную записку и дополнение по выбранной школе. Титульные листы разделены по школе и виду документа; PDF формируется исходными шаблонами mPDF. Учебный период берётся из интерфейса. Для дополнения служебной записки используются её номер, дата и вид изменений; реквизиты исходного распоряжения и основание нужны для общего распоряжения.

`GET /api/v1/oop/status` доступен только admin. Таблица читает `program_list` и `mep_status`, поддерживает серверный поиск, фильтры и последовательную загрузку по 50 записей. Отсутствующий статус обозначается «Не указан», утверждение не вычисляется автоматически. РОП не видит страницу в меню, карточках и поиске; прямой запрос API получает 403. Схема БД не изменялась.

Проверки: `backend/tests/ppa.php` (изолированные временные таблицы), `backend/tests/ppa-browser.mjs`, `backend/tests/oop-status-browser.mjs` (чтение и проверка доступа без изменения рабочих данных).


### Формирование ООП

`GET /api/v1/oop/formation?program=<id_mep>` и `POST /api/v1/oop/formation` подключены к существующей БД. Форма использует `tasks_mep_3`, `mep_status`, связи `program_*` и матрицы компетенций. Изменения сохраняются атомарно с проверкой версии; очищенные поля действительно очищаются. Нулевые кадровые показатели сохраняются. Форматы существующих текстовых дат не преобразуются.

Стандарты, области ПД, задачи, объекты и ПК СУОС выбираются из связанных справочников направления. Типы задач выводятся из выбранных задач. ПК ООП редактируются с привязкой к задачам и объектам; общие строки без `id_mep` сохраняются без изменения из формы отдельной программы. УК/ОПК и сведения направления может менять только admin. Трудоёмкость и сроки отображаются из общих нормативных сведений, а не сохраняются как произвольные поля ООП.

По согласованию статус могут менять admin и РОП. Для РОП утверждённая ООП закрыта для правок до возврата в черновик. Смена статуса отображается в административной таблице проверки статуса. Схема БД и печатные шаблоны не изменялись. Сохранение формы больше не использует localStorage; отдельные исходные страницы и модуль печати подключаются независимо.

Проверки: `backend/tests/oop.php` — временные таблицы, сохранение и очистка, связи, матрицы, роли, статусы, конфликт версий; `backend/tests/oop-browser.mjs` — чтение настоящих данных, защита переходов, обе роли и мобильная ширина без изменения рабочих записей.

### Исходные данные образовательных программ

Подключены матрица ПК ООП и формы обучения: `/api/v1/oop/program-data/{matrix|forms}/{list|save|delete}`. Таблицы используют те же `matrix_pk_oop` и `program_education_form`, что и формирование ООП. Поиск и фильтр программы выполняются на сервере, выдача загружается порциями. Изменение и удаление проверяют версию строки; повторная форма обучения отклоняется. РОП не может менять утверждённую ООП. Общие компетенции без программы отображаются отдельно и не редактируются как записи отдельной программы.

Проверки: `backend/tests/oop-program-data.php` (временные таблицы) и `backend/tests/oop-program-data-browser.mjs` (чтение таблиц и открытие редакторов без сохранения рабочих данных).

### Печать ООП

`POST /api/v1/oop/print` с `program: id_mep` формирует PDF из БД через mPDF. Основа — исходный `legacy_poly/pdf/ohop.php`, перенесённый в `backend/templates/oop/document.php`: сохранены титульные листы, оглавление, размеры полей, Times, альбомные матрицы, приложения и специальные условия шаблона. Год берётся из титульного листа ООП. Флаг `tasks_mep_3.display` управляет разделом 8.4. Интерфейс использует серверный выбор программ, предпросмотр PDF, скачивание и печать самого PDF.

Убраны зависимости от старой сессии и соединения с БД, вспомогательные HTML-формы не вызываются при печати. Значения из БД очищаются от исполняемых и внешних ресурсов. Сверены рендеры для трёх уровней образования: 36, 27 и 37 страниц; при использованных данных изображения совпали с рендером перенесённого шаблона без очистки. Проверка интерфейса: `backend/tests/oop-print-browser.mjs`.

### Общие исходные данные и сведения по направлениям

`/api/v1/oop/general/{areas|types|standards|uk}/{list|save|delete}` и `/api/v1/oop/directions/{areas|tasks|objects|standards|pk|opk}/{list|save|delete}` работают с существующими таблицами PostgreSQL и доступны только admin. Поиск выполняется по всей выборке, списки используют курсорную подгрузку. Формы проверяют связи и версию записи; удаление используемых записей и перенос между направлениями блокируются. Матрица УК применяется по уровню обучения. Схема БД не меняется.

Проверки: `php backend/tests/oop-general.php`, `php backend/tests/oop-directions.php` (запись только во временные таблицы). Браузерные проверки в одноимённых `*-browser.mjs` используют переменные `TEST_ADMIN_PASSWORD`, `TEST_ROP_PASSWORD` и не изменяют рабочие данные.

### Базы учебных периодов

Admin управляет базами на `/databases`. JSON-реестр `backend/var/databases.json` хранит название, техническое имя PostgreSQL, учебный период, состояние копии и один `defaultId`. Каталог `var` исключён из Git и не публикуется веб-сервером. Реестр нужно резервировать вместе с настройками. Параметры подключения общие из `db`; рабочая схема не изменяется. Архив остаётся общим.

При входе база по умолчанию закрепляется в серверной сессии. Переключение меняет базу и период, проверяет наличие пользователя в целевой базе и обновляет токен контекста. API-клиент отправляет `X-Database-Context`; изменения со старым токеном отклоняются. Уже открытые сессии не меняются при назначении новой базы по умолчанию. Авторизация использует существующую таблицу пользователей; отдельная база авторизации сейчас не создаётся.

Создание копии выполняется фоновым PHP CLI через `pg_dump` / `pg_restore`, без отключения пользователей исходной базы. На Windows процесс запускается скрыто. Параметры `postgres_bin` и `php_cli` в серверной конфигурации позволяют указать исполняемые файлы; по умолчанию используются установленный PostgreSQL и PHP CLI рядом с текущим PHP. У пользователя PostgreSQL должно быть право создания БД. Пароль передаётся процессам в окружении, не в аргументах команд. Поддерживается одна операция копирования одновременно.

Новая база доступна только после завершения восстановления. Назначение её основной происходит после успешного копирования и не отменяет более позднее решение admin. Все записи копируются, автоматической очистки комиссий/статусов нет. Настройки нумерации ГЭК изолированы по имени БД; архив не разделяется. При ошибке или остановке процесса база остаётся недоступной, журнал — `backend/var/database-copies/<id>.log`. Частичные БД автоматически не удаляются. После исправления причины можно создать копию под новым именем; удаление частичной БД выполняется отдельно администратором PostgreSQL.

Для изолированного тестового сервера можно задать `POLYTECH_CONFIG` — путь к отдельному PHP-файлу конфигурации. Проверки API: `backend/tests/databases.mjs` с `TEST_DATABASE_URL`, `TEST_ADMIN_PASSWORD`, `TEST_ROP_PASSWORD`; запускать только против изолированной тестовой БД. Проверки интерфейса: `backend/tests/databases-browser.mjs` (без изменений рабочих данных).
