# План реализации бэкенда и подключения фронтенда

Дата: 10.09.2026. Этапы 1–2 реализованы: PHP API, существующая БД, реальный вход/выход, сессии, обработка ошибок и роли. Проверены вход двумя пользователями, CSRF и запреты РОП. Бизнес-операции и официальная печать подключаются следующими этапами. Инструкция: [backend/README.md](backend/README.md).

## 1. Обязательные договорённости

- Бэкенд должен решать те же прикладные задачи, что и прежняя система. Сохраняем смысл операций, связи данных, варианты формирования документов и обязательные правила.
- Нужная PostgreSQL уже развёрнута. Не создаём новую рабочую БД, не восстанавливаем поверх неё резервную копию и не меняем её схему. Для проверки операций записи используем отдельную тестовую копию существующей схемы и согласованные тестовые данные.
- Имя ранее восстановленной локальной БД: `legacy_poly`, сервер PostgreSQL 17, адрес `localhost:5432`, пользователь `postgres`. Это зафиксировано в отчёте восстановления `../legacy_poly-overview.md`: источником был `db07092026.backup`. В старом `connect.php` осталось другое имя по умолчанию (`Metodika`); его нельзя автоматически считать целевой БД нового API. Проверка текущего подключения без пароля не прошла, поэтому сведения о восстановлении не выдаются за новую проверку доступности.
- Старый код — источник сведений о поведении, но не безусловный образец корректности. Ошибки логики, неверные обновления, потерю данных, отсутствие проверки и сообщений об ошибках исправляем.
- Отличаем дефект от обязательного требования. Неясное поведение, хардкод, противоречия между кодом и реальным процессом обсуждаем с пользователем до изменения. Догадки не становятся бизнес-правилами.
- Это правило относится ко всей системе, не только к печати. Ожидаем, что действующие правила определены: сначала ищем ответ в старом поведении, данных и договорённостях. Не создаём искусственных согласований для ясных требований и подтверждённых ошибок. Если реальная неоднозначность всё же обнаружена, уточняем её у пользователя до спорного изменения.
- Печать — жёсткий стандарт. Итоговые документы должны соответствовать прежним утверждённым документам: содержание, формулировки, порядок, шрифты, размеры, поля, таблицы, переносы, подписи, нумерация и ориентация страниц. Любые вопросы и спорные расхождения согласовываем с пользователем.
- Сохраняем принятый фронтенд, пять основных разделов, привычный путь, единые таблицы и названия действий. Регистрацию и новые процессы согласования самостоятельно не добавляем.
- Согласованы роли: `admin` — администратор, `rop` — РОП. РОП не видит и не может открывать «Исходные для направлений» и «Общие исходные данные всех образовательных программ». Запрет действует в меню, карточках, поиске, прямых маршрутах и API. Другие ограничения не добавляются. В БД нет поля роли: назначение хранится в серверной конфигурации; неизвестной роли доступ закрыт.
- Версия 1.0 — обозначение интерфейса. Оно не означает, что сервер, реальная авторизация и официальная печать уже подключены.

Эти требования имеют приоритет перед более ранними заметками о прототипе.

## 2. Что есть сейчас и что предстоит соединить

Фронтенд работает на React и TypeScript. Комиссии, справочники и формы сохраняются в нескольких независимых локальных хранилищах; архив — в IndexedDB. Вход проверяется в браузере. Общие таблицы ООП, таблицы направлений и карточки программ ещё не образуют единый источник данных. README содержит исторические описания этапов и не заменяет проверку текущего кода.

Прежняя система использует PHP, PostgreSQL и существующие обработчики печати, в том числе mPDF. В схеме есть отдельные таблицы и связи для ГЭК, СПО, аттестации, программ, направлений, матриц компетенций и пользователей. Их точное назначение проверяем по запросам старого приложения и фактической схеме развёрнутой БД, не только по названиям.

Главный результат: сохранённые на сервере данные видны другим пользователям, одинаково используются в справочниках, комиссиях, ООП и печати; ошибки не оставляют частично записанных документов.

## 3. Предлагаемая архитектура без лишних работ

Предпочтительный начальный вариант — отдельный PHP JSON API рядом с текущим приложением. Это позволяет переиспользовать знание схемы и существующий механизм печати. Окончательное решение принимаем после проверки серверного окружения; смена языка сама по себе не является задачей проекта.

```text
React → /api/v1 → обработчики запросов → прикладные операции → PostgreSQL
                      ├─ существующий механизм печати → готовые документы
                      └─ файловое хранилище архива
```

- Один серверный проект с разделением по модулям. Без микросервисов, очередей и дополнительных систем, пока их необходимость не подтверждена.
- SQL с параметрами и явным отображением полей API на существующие таблицы. Без автоматических миграций и подгонки БД под объектную модель фронтенда.
- Фронтенд и API желательно публиковать на одном домене. В разработке обращения `/api` перенаправляются на локальный сервер.
- Конфигурация подключения хранится вне исходного кода. Данные доступа к PostgreSQL не передаются браузеру и не публикуются в Git.
- Рабочие файлы архива хранятся вне исходников и публичного каталога сайта. Новые таблицы для архива без согласования не добавляются.
- Сначала сохраняем действующий механизм печати за контролируемым серверным обработчиком. Перенос движка печати — отдельное решение после доказанной совместимости.

## 4. Разведка и карта соответствий — первый этап

Для каждой операции составить короткую карту: экран → действие → старый обработчик → таблицы и поля → обязательные условия → печатные документы. Отдельно записать, что подтверждено кодом, что проверено на данных и что требует ответа пользователя.

Проверить:

1. Фактические ключи, типы, связи, последовательности и ограничения развёрнутой БД; сопоставить с имеющимся файлом схемы.
2. Кодирование учебного периода. Метка `2026/2027` в интерфейсе не должна произвольно менять год или способ выбора данных в старой системе.
3. Возможную зависимость периода от выбранной базы: старое подключение использует значение БД в сессии. Не давать браузеру передавать произвольное имя базы.
4. Числовые идентификаторы старых записей и локальные UUID фронтенда. Локальные записи автоматически в рабочую БД не переносить.
5. Связи одного направления с несколькими программами; различия общих данных, данных направления и данных отдельной программы.
6. Источник статусов ООП, допустимые переходы и полномочия. Не приравнивать заполненность к утверждению.
7. Председателей и внешних членов: сотрудник может быть председателем; формы зависят от сферы деятельности; комплексная ГЭК может относиться к нескольким школам.
8. Фиксированные председатели, директора и и.о., правила нумерации, выбора школы, дополнений и изменений СПО/АК/ППА.
9. Действительные ограничения доступа. Наличие только `user_list` не доказывает наличие ролей — не вводить новую модель ролей без необходимости.

Результат этапа: карта соответствий, перечень найденных дефектов, список вопросов и набор эталонных документов. До выяснения спорной операции её серверную запись не включать.

## 5. Как вести бэкенд и фронтенд параллельно

Параллельная работа означает согласованные задачи двух частей приложения, а не два независимых варианта логики.

| Шаг для каждого модуля | Бэкенд | Фронтенд | Совместная проверка |
|---|---|---|---|
| Контракт | Описать запросы, ответы, поля, ошибки и права | Сверить с формами и сценариями | Зафиксировать контракт API и примеры |
| Чтение | Вернуть данные из существующих таблиц | Подключить API через слой доступа к данным | Сверить реальные записи со старой системой |
| Запись | Реализовать проверки и транзакции | Подключить сохранение, ожидание ответа, ошибки полей | Создать, изменить, перечитать запись |
| Связи | Проверить существование и допустимость связей | Выбирать идентификаторы из справочников | Проверить зависимые экраны и запрет недопустимого удаления |
| Печать | Сформировать документ из сохранённых данных | Показать результат сервера, скачать и распечатать | Сравнить с утверждённым эталоном |
| Завершение | Пройти интеграционные проверки | Убрать локальное сохранение модуля | Пройти весь пользовательский сценарий |

До готовности сервера фронтенд использует тестовый поставщик данных с тем же контрактом. Переключение на API выполняется для согласованного модуля и его зависимостей. Нельзя при ошибке API молча сохранять изменения локально или смешивать реальные идентификаторы с тестовыми.

Один набор типов запросов и ответов и одна спецификация API. Изменение контракта одновременно сопровождается исправлением клиента и проверками. До первой интеграции не нужно завершать весь бэкенд: первый рабочий путь — вход, чтение справочника, изменение записи и повторное чтение.

## 6. Порядок подключения модулей

| Этап | Серверная часть | Изменения фронтенда | Условие завершения |
|---|---|---|---|
| 1. Основа | Подключение к существующей БД, обработка ошибок, проверка сессии, журнал ошибок | Общий API-клиент, состояния загрузки и недоступности | Ошибка сервера видна пользователю и не теряет ввод |
| 2. Вход | Вход и выход, серверная сессия, защита запросов изменения | Убрать проверку фиксированных реквизитов в браузере | Вход реальным пользователем, истечение сессии и выход проверены |
| 3. Справочники | Школы и директора, направления, программы, преподаватели, дисциплины, люди и председатели | Подключить существующие таблицы и селекторы к API | Одна запись используется во всех связанных экранах |
| 4. ГЭК | Список, создание, состав, программы, выбор председателя и секретаря, удаление | Подключить список, карточку и сохранение целиком | Полный путь ГЭК и первая официальная печатная форма сверены |
| 5. СПО/АК/ППА | Правила каждого вида, титульные листы, изменения и дополнения | Подключить существующие конструкторы и документы | Все предусмотренные старой системой варианты работают |
| 6. Общие данные ООП | Области ПД, типы задач, профстандарты, матрица УК с уровнем обучения | Подключить общие справочники | Связи используют реальные идентификаторы, не копии текста |
| 7. Данные направлений | Сферы, задачи, объекты, связи стандартов, ПК СУОС, ОПК | Подключить таблицы направлений и зависимые селекторы | Данные направления корректно доступны нескольким программам |
| 8. Данные программ и ООП | ПК ООП, формы обучения, сведения документа и статусы | Соединить исходные данные, заполнение, статус и печать | Изменение данных отражается в нужной программе без потери других сведений |
| 9. Архив | Папки, загрузка, скачивание, переименование, удаление | Заменить IndexedDB серверными операциями | Вложения доступны после входа с другого компьютера |
| 10. Ввод в работу | Проверка окружения, резервной копии и восстановления | Проверка всех пяти разделов | Приёмка пользователя и проверенный возврат на предыдущую версию |

Архив можно разрабатывать параллельно со справочниками после готовности авторизации. Исследование и проверку печати начинаем на первом этапе, а не откладываем до конца разработки. Полную ООП подключаем после её источников данных.

## 7. Сохранение и ошибки

- Сервер повторно проверяет все значимые условия независимо от фронтенда: обязательные поля, допустимость ссылок, номера, типы и ограничения операций.
- Комиссию с составом и связанными программами сохраняем одной транзакцией. При сбое отменяется вся операция. Для ООП заранее фиксируем границы сохранения раздела и его связанных данных.
- Данные справочника не копируем без необходимости в каждую комиссию или программу. Исключение — существующий обязательный исторический снимок, если он предусмотрен старой системой.
- Ошибка содержит понятный текст, код и, при необходимости, ошибки отдельных полей. SQL, трассировки и реквизиты подключения пользователю не выводятся.
- Используем различимые ответы: нет сессии, нет доступа, запись не найдена, конфликт, неверные данные, ошибка сервера. Сообщение «Сохранено» появляется только после подтверждения сервера.
- При неудачном сохранении введённые значения остаются в форме. Кнопка защищена от повторного нажатия; неоднозначный сетевой сбой не приводит к автоматическому повторному созданию записи.
- Несохранённые изменения продолжают защищаться при переходах и смене программы. Ошибка загрузки не изображается пустой таблицей.
- Конкурирующее редактирование не должно незаметно затирать чужие изменения. Без изменения схемы можно проверять серверный отпечаток исходного состояния в транзакции; точный способ выбирается для каждой сущности. Учитываем, что старое приложение может ещё записывать в те же таблицы.
- Удаление связанных записей проверяется сервером. Каскадное удаление не добавляется по предположению; при зависимости показываем понятную причину отказа.

## 8. Авторизация без расширения задачи

Используем существующих пользователей. Новую регистрацию не делаем. Сессия проверяется на сервере при каждом закрытом запросе, включая печать и скачивание файлов. После входа обновляется идентификатор сессии; cookie недоступна JavaScript, для рабочего HTTPS включаются соответствующие защитные параметры. Запросы изменения защищаются от CSRF. Запросы к БД параметризуются.

В старом входе обнаружено прямое включение введённых строк в SQL и сравнение пароля с содержимым поля БД. Это нужно исправить, а не переносить буквально. Способ перехода к безопасной проверке существующих паролей согласовать до изменения их хранения: не менять реквизиты пользователей или формат поля самовольно. Секреты не включать в план, логи и Git.

## 9. Печать: обязательный контроль совместимости

Текущие браузерные макеты React не являются эталоном. Эталон — подтверждённый пользователем документ прежней системы. Пользовательская формулировка: итоговый формат должен быть аналогичен прежнему, поскольку действует жёсткий стандарт.

1. Собрать реестр всех видов печати: ГЭК, председатели обычных и комплексных комиссий по сферам, секретари, СПО/АК/ППА, титульные листы, дополнения и изменения, ООП. Уточнить полный набор по меню старой системы.
2. Для каждого вида зафиксировать источник данных, параметры, группировку, сортировку и область выбора: школа, все школы, программа и другие предусмотренные варианты.
3. Получить эталонные файлы и подтверждение, какие версии шаблонов актуальны. Сохранить контрольные копии и идентификаторы версий шаблонов.
4. Зафиксировать окружение формирования: движок, шрифты и их файлы, параметры страницы. Обновление библиотеки может изменить переносы даже при неизменном шаблоне — проверять это отдельно.
5. Подключить серверное формирование по существующему шаблону и сохранённым данным. Для официального результата фронтенд открывает сформированный файл, а не печатает страницу интерфейса.
6. Проверять документ на одних и тех же данных в старом и новом пути: текст и реквизиты, количество и размеры страниц, геометрию таблиц, подписи и переносы. Сравнение изображения страниц дополнить проверкой содержимого; побайтовое совпадение PDF не требуется из-за служебных метаданных.
7. Включить случаи длинных ФИО и должностей, много участников/программ, пустые необязательные поля, несколько школ, разные сферы председателей и уровни/формы обучения ООП. Проверить границы страниц и многостраничные таблицы.
8. Выполнить контрольную печать с согласованным масштабом и настройками принтера. Зафиксировать приёмку пользователем.

Если исправление ошибки данных меняет печатный результат, показать конкретное различие пользователю. Нельзя автоматически «улучшать» утверждённый текст, объединять разные формы, убирать подписи, менять состав колонок или считать React-макет заменой стандарта. При неоднозначности остановить только спорную часть и задать вопрос, продолжая независимые работы.

## 10. Архив

Сначала определить действующий корневой каталог архива и правила доступа. Не переносить и не переименовывать рабочие файлы автоматически. При подключении использовать серверные идентификаторы или проверенные относительные пути; любые пути должны оставаться внутри разрешённого корня, включая обработку ссылок файловой системы.

Проверить вложенные папки, русские имена, одинаковые имена файлов, прерванную загрузку, отсутствие прав, заполненный диск и удаление папки с содержимым. Не показывать успешную загрузку до её завершения. Локальные файлы из IndexedDB переносить только отдельной явно выбранной операцией пользователя.

## 11. Приёмка и переключение

- Проверки записи выполняются на тестовой копии; рабочая БД не очищается и не заполняется тестовыми данными.
- Для каждого модуля пройти путь от входа до сохранения, повторного открытия и нужной печати. Проверить работу двух пользователей и отказ сервера.
- Перед включением рабочего режима подготовить резервную копию данных и файлов, проверить возможность восстановления и совместимость со старым приложением.
- Старый и новый интерфейсы при совместной работе должны использовать совместимые операции. Если это не доказано, не открывать одновременную запись в спорный модуль до согласованного переключения.
- План возврата: предыдущая версия приложения и совместимые обработчики. Не откатывать всю рабочую БД поверх новых пользовательских изменений как обычный способ возврата интерфейса.
- После подключения модуля удалить его локальный источник данных из рабочего пути. При недоступности сервера показывать ошибку, а не незаметно возвращаться к локальным данным.
- Считать модуль готовым, когда проверены реальные данные, ошибки, зависимости и все относящиеся к нему печатные формы. Успешная сборка фронтенда сама по себе не является приёмкой.

## 12. Вопросы, которые решаем с пользователем по мере реализации

- Какая установка старой системы и какие документы являются окончательным эталоном? Какие варианты печати используются фактически?
- Какие обнаруженные расхождения — ошибки, а какие — обязательные исключения или хардкод?
- Какие пользователи выполняют утверждение, удаление и исправление документов? Есть ли ограничения, не отражённые явно в коде?
- Как именно выбранный учебный период связан с данными и подключением к БД?
- Допустимо ли совместное редактирование старым и новым интерфейсом в период перехода?
- Как согласовать переход существующих паролей на безопасную проверку, не нарушив вход пользователей?
- Где расположен рабочий архив и какой порядок его подключения и резервного копирования принят?

Не требуется ответить на весь список заранее. Вопрос задаётся тогда, когда конкретное решение зависит от ответа. По печати и неоднозначной бизнес-логике предположения без согласования недопустимы.
